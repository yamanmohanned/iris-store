# ملخص المرحلة 3 — التسجيل والتحقق والصلاحيات والأمان

**الحالة:** ✅ مكتملة · **الفرع:** `claude/nifty-turing-csz4ep` · التفاصيل الكاملة في [`docs/SECURITY.md`](../SECURITY.md)

## ما تم إنجازه

### 1) نظام الحسابات (Better Auth 1.7 + Argon2id)

| الميزة                       | كيف تعمل                                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| إنشاء حساب                   | الاسم + البريد + كلمة المرور ← **رمز من 6 أرقام يصل للبريد** ← تأكيد ← دخول تلقائي.                                    |
| تسجيل الدخول                 | بكلمة المرور، **أو برمز يصل للبريد بدون كلمة مرور** (للزبائن)، أو Google (اختياري عند ضبط المفاتيح).                   |
| نسيت كلمة المرور             | رمز عبر البريد ← كلمة مرور جديدة ← **تسجيل الخروج من كل الأجهزة**.                                                     |
| التحقق بخطوتين               | تطبيق مصادقة (QR) + 10 رموز احتياطية + خيار "الوثوق بالجهاز 7 أيام".                                                   |
| صفحة "الأمان" للحساب         | تفعيل 2FA، تغيير كلمة المرور، **قائمة الأجهزة المسجّلة وتسجيل الخروج منها**.                                           |
| معالج الإعداد الأول `/setup` | يُنشئ المالك ويجهّز المتجر حسب الدولة؛ محمي بـ `SETUP_TOKEN` ويُغلق نهائياً بعده. بديل سطر أوامر: `pnpm create-owner`. |

### 2) قرارات أمنية مهمة اتُّخذت

- **اكتشاف وإصلاح ثغرة في المكتبة:** الدخول برمز البريد أو Google **يتجاوز التحقق بخطوتين** في Better Auth،
  لذلك مُنعت هذه الطرق لحسابات الإدارة على مستوى قاعدة البيانات (Hook)، ولا تُرسل رموز دخول لبريد الموظفين أصلاً.
- **لا واجهة JSON مكشوفة للمصادقة:** كل العمليات عبر Server Actions (تحقق + Captcha + قفل + حدود)،
  ومن نقاط Better Auth لا يُفتح إلا رابط العودة من Google.
- **عدم كشف الحسابات:** التسجيل ببريد مسجّل يعطي الرد نفسه (ويصل لصاحب البريد تنبيه).
- **قفل الحساب** بعد 8 محاولات خاطئة (15 دقيقة)، و**تحديد معدل** لكل العمليات الحساسة (جدول في SECURITY.md).
- **الإدارة:** 2FA إلزامي قبل دخول `/admin`، الجلسة الإدارية تنتهي كل 24 ساعة، الزبون يرى 404.
- **الأدوار:** مالك، مدير، مدير منتجات، مدير طلبات، زبون — تُفحص على الخادم في كل عملية.
- **إصلاح خلل دقيق:** عند تفعيل 2FA أو تغيير كلمة المرور تتغير الجلسة؛ كانت الصفحة تقرأ الجلسة القديمة
  فتعيد التوجيه لصفحة الدخول. الحل: قراءة الكوكيز من المخزن الحي للطلب (`authHeaders`).

### 3) البريد الإلكتروني

- طبقة مزودين: `console` (تطوير) / `smtp` / `resend`، مع إعادة محاولة.
- قوالب عربية/إنجليزية بهوية المتجر ولونه (رمز التحقق، تنبيه محاولة التسجيل ببريد موجود).
- الرسائل تُرسل **في الخلفية** (لا يكشف التوقيت وجود الحساب).

### 4) الواجهات (Mobile-first)

صفحات: الدخول، الدخول برمز، إنشاء حساب، تأكيد البريد، نسيت كلمة المرور، كلمة مرور جديدة، التحقق بخطوتين،
الإعداد الأول، حسابي، الأمان. حقل الرمز يفتح لوحة الأرقام في الهاتف، يقبل الأرقام العربية، ويدعم التعبئة
التلقائية من الرسائل، ويُرسل تلقائياً عند اكتمال 6 أرقام. زر إظهار كلمة المرور، عدّاد إعادة الإرسال،
رسائل خطأ مترجمة مع الإبقاء على ما كتبه المستخدم.

## الاختبارات

- **72 اختبار وحدات وتكامل** (منها 12 لتدفقات المصادقة على قاعدة بيانات حقيقية: التسجيل، عدم الكشف،
  كلمات المرور الضعيفة، منع تحديد الدور، القفل، الاستعادة، حد محاولات الرمز، منع الموظفين من الدخول بالرمز،
  الحسابات الموقوفة، تفعيل 2FA وفرضه).
- **21 اختبار متصفح (E2E)** على الهاتف والحاسوب: تسجيل حقيقي برمز من البريد، دخول/خروج، الدخول برمز،
  رسالة الخطأ، إخفاء الإدارة عن الزبائن، معالج الإعداد ← إجبار 2FA ← لوحة التحكم ← دخول بالرمز الاحتياطي.

## ملاحظات للمالك

- بدون ضبط مزود بريد (`EMAIL_DRIVER`) لن تصل رموز التحقق للزبائن (الشراء كزائر يبقى متاحاً).
- بعد إنشاء حساب المالك احذف `SETUP_TOKEN` من الإعدادات.
